# TASK: Comprehensive Audit of Frontend and Simulation Integration

You are an expert system architect and software auditor specializing in IoT systems, React/TypeScript frontends, and Node.js/Express backend APIs.

Your mandate is to perform an exhaustive, evidence-based code and architectural audit of the integration between the **Frontend** and the **Device Simulation** in this repository (`iot-water-filtration-system`).

Do not make assumptions or superficial observations. Inspect actual source code, trace data structures end-to-end, verify type definitions, compare runtime contracts, and verify compliance with repository governance rules (`AGENTS.md` and `docs/`).

### Audit Dimensions (Detailed Checklist)

Conduct your audit across these 7 distinct dimensions:

#### Dimension 1: Telemetry Pipeline & End-to-End Traceability
- Trace a sensor reading batch generated by `liveSimulator.ts` through:
  `buildReadingBatch()` -> `POST /devices/:id/readings` -> `sensor_readings` table -> `GET /telemetry/current` / `GET /telemetry` -> `telemetryService` -> `SensorGrid` / `DashboardPage` / `HistoryPage`.
- Are all 10 sensors (5 pre-filtration, 5 post-filtration: `ph`, `turbidity`, `tds`, `temperature`, `flow_rate`) correctly captured, persisted, and surfaced in the UI?
- Are timestamp formats preserved (ISO 8601 UTC) and rendered accurately with timezone awareness (`Asia/Manila`)?

#### Dimension 2: Contract, Schema, and Naming Alignment
- Check vocabulary consistency:
  - Simulator & DB: `category` (`ph`, `turbidity`, `tds`, `temperature`, `flow_rate`), `position` (`pre_filtration`, `post_filtration`).
  - Frontend types: `parameter` (`pH`, `turbidity`, `TDS`, `temperature`, `flowRate`), `stage` (`before`, `after`).
  - Verify every mapper in `backend/src/lib/mappers.ts` and ensure no parameter is dropped, mistranslated, or undefined.
- Verify unit representations:
  - Are units in `liveSimulator.ts` (`pH`, `NTU`, `ppm`, `°C`, `L/min`) identical to what frontend components and formatters expect?
- Check device status contract:
  - Backend `toDeviceStatus()` in `mappers.ts` does NOT return `is_simulated`.
  - Frontend `deviceService.ts` fetches `GET /devices`, grabs `devices[0].is_simulated`, and combines it with `GET /devices/:id/status`.
  - Audit the risks and edge cases of this pattern (e.g. multiple devices, empty device list, network race conditions).

#### Dimension 3: Simulation State & Provenance Identification (AGENTS.md Compliance)
- According to `AGENTS.md` and `docs/ARCHITECTURE.md`:
  - "Simulator records must remain explicitly identified as simulated data and must not be presented as real experimental or laboratory results."
  - "Never disguise simulated data as real experimental or laboratory data."
  - "Sensor readings must not be presented as laboratory proof that water is safe to drink."
- Audit whether the frontend UI clearly and unambiguously displays that data originates from a simulated device when `is_simulated = true`.
- Check whether `DashboardPage.tsx`, `HistoryPage.tsx`, `TestRunsPage.tsx`, and `LaboratoryValidationPage.tsx` maintain strict isolation between simulated telemetry and validated laboratory records.
- Check if export features (e.g. CSV export in `HistoryPage.tsx` or `/export/csv`) clearly tag data as simulated or note device provenance.

#### Dimension 4: Real-time Streaming vs Static Polling Gap
- The backend features `GET /telemetry/stream` and `GET /realtime/stream` implementing Server-Sent Events (SSE).
- The simulator (`liveSimulator.ts`) posts fresh readings every 5 seconds (`LIVE_SIM_INTERVAL_MS`).
- Inspect `frontend/src/hooks/useServiceData.ts` and active pages. Does the frontend connect to the SSE streams or poll on an interval?
- If the frontend only executes a one-time fetch on mount, analyze the consequences: Does the live simulator update the dashboard in real-time? What changes are required to achieve live dashboard updates?

#### Dimension 5: Edge Cases, Null Handling & Fault Simulation
- `liveSimulator.ts` simulates unavailable sensors (~3% probability) with `value: null` and `status: 'unavailable'`.
- Trace how `null` values propagate:
  - How does `devices.routes.ts` handle null values?
  - How does `alertEngine.ts` respond to `status: 'unavailable'`?
  - How does `toSensorReadings()` and `groupReadingsIntoTelemetry()` handle null or missing values? (Notice that `toSensorReadings` filters out nulls!)
  - What happens in `SensorGrid.tsx` when a sensor reading is missing or null? Does it disappear, throw an error, or show a fallback?
  - Does `formatSensorValue(parameter, reading.value)` in `frontend/src/utils/formatters.ts` crash on null/undefined (`value.toFixed(...)`)?
  - What happens in `HistoryPage.tsx` table when null/undefined values are rendered?
  - When the simulator process is stopped, does `deviceWatchdog.ts` trigger an offline alert, and does the frontend reflect device disconnection?

#### Dimension 6: Test Run & Session Correlation
- In `liveSimulator.ts`, `buildReadingBatch()` posts readings without a `testRunId`.
- Examine how this affects `test_runs` metrics (`telemetryCount`, `duration`, `processedVolume` in `backend/src/lib/testRunHydrator.ts`).
- Can simulated telemetry ever be attached to an active test run created from the frontend? How would a user or tester link simulated readings to a test run?

#### Dimension 7: Architectural Cleanliness & Project Discipline
- Audit the purpose and status of the top-level `simulator/` directory (`.gitkeep` only). Check against `docs/DEVELOPMENT.md` and `README.md`.
- Are mock fixtures under `frontend/src/data/mock/` still referenced anywhere, or are they cleanly decoupled from active services?
- Confirm no credentials, secrets, or service-role keys are exposed in frontend code, simulator scripts, or environment examples.

   - Prioritized list of fixes for Nash (Frontend), Alejandro (Backend), and Edgar (Hardware/Firmware).
